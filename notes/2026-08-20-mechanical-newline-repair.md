# 2026-08-20 字符串断行损坏的机械修复（撤销"必须跨模型修复"结论）

## 背景
2026-08-19 结论：GLM 流式管线把字符串字面量内的 `\n` 转义替换为真实换行，
属管线级损坏，prompt 防不住，需 deepseek 修复级兜底（glm→deepseek 15/15 vs deepseek 单独 2/9）。

## 今日推翻该结论的部分
该变换是**双射**：模型写 `\n`（2 字符转义）→ 管线换成真实换行（1 字符）。
逆向：字符串态遇到真实换行 → 写回 `\n` 字面量。往返无损。

关键安全性论证：JS/TS 中双引号/单引号字符串**在语法上不可能合法包含裸换行**，
所以修复器只会在"语法上必然是损坏"的状态上触发——对合法代码零误伤。
模板字符串 `` ` `` 内换行合法，跳过不修；注释先跳过（防注释里的引号/撇号干扰状态机）。

## 实现（src/delegate.ts）
- `repairBareNewlinesInStrings`：引号/转义/行注释/块注释状态机；fence 与 bare-code
  两条路径均在 normalizeSmartQuotes 之后接入（先弯引号转直，再修断行）。
- 顺带发现并修复**fence 截断 bug**：产物代码字符串内嵌 ` ``` `（如测试提取器的代码）
  会使非贪婪 fence 正则提前截断。救援策略：候选 A=首个配对，候选 B=首开栏→最后一个
  ``` 的跨度；仅当 A 的 `bracketImbalance`≠0 且 B=0 时采用 B（最小干预，多块回答行为不变）。
- `bracketImbalance`（新）：数 `()[]{}` 三类括号，仅供 fence 救援判定；
  验收仍用只数 `{}` 的 `braceImbalance`，避免正则字面量中的转义括号误报。

## 验证
- 真实损坏样本（fixtures/glm-smartquote-multiline.txt，弯引号+断行+嵌套``` 三重损坏）
  → 规则修复后 node --check 通过。
- 合成边界：模板串真实换行保留、`\"`/`\'` 转义、注释撇号——修复后可执行。
- 回归 28/28（含新增 4 条固化测试）。

## 边界与残留
- 修复器是 JS/TS 语义；Python 三引号字符串合法跨行，不适用（当前 executor 首选 deepseek，不受影响）。
- 若 GLM 管线未来出现"丢字节"型（而非"重排版"型）损坏，规则不可逆，仍需跨模型兜底。
- glm 是否因此升格为 code executor：待一次真实 web_delegate 端到端验证后再动 roles，
  目前 executor 链维持 deepseek 优先。

## 第二波（同日晚）：历史重放暴露的两层新问题

用 scripts/replay-glm-history.mjs 只读重放 GLM 全部历史（13 条），4 条断行损坏全部
机械还原、语法通过。过程中新发现并处理：

1. **弯引号定界 + 内容直引号**（`“{"a":1}”`）：盲转产出 `"{"a":1}"` 后无法消歧。
   normalizeSmartQuotes 改为成对感知：趁弯定界符还携带边界信息时给内容直引号加 `\"`，
   孤儿弯引号再兜底盲转。该修复是历史 4 条通过的必要条件（去掉即回退）。
2. **悬挂 fence 段**：GLM 历史渲染会在真闭合后多出一个孤立 ``` 段（可能来自空 PRE），
   劫持 lastIndexOf 救援锚点。救援 span 尾部剥离裸 fence 行（spanTrimmed）。
   注意：曾尝试全局剥离"空 fence 块"的正则——会把相邻块的 闭合+空白+开栏 一起吞掉，
   造成全面回归，已回滚。教训：跨块全局正则不可靠，结构感知的局部处理才安全。
3. **已知边界（未解）——混合定界符**：idx-12（自指性提取器测试代码）出现
   `test(“...fails", () => {...const raw = "Answer:...thanks”;`——同一行内弯开直闭、
   直开弯闭并存，弯引号配对跨段误转义。无局部规则可消歧（信息论上歧义）。
   下一步设计（已定未实施）：**语法反馈修复循环**——候选重构逐个过 `node:vm` 的
   Script 真语法解析（零依赖、不执行），按首个 SyntaxError 位置应用微修复菜单
   （改转义/改配对），循环收敛。这把"猜配对"变成"解析器裁决"。

## 定案（用户拍板）：默认提取器 + deepseek 修复兜底

架构两层，2026-08-20 实施并实测：

**第一层（默认）**：机械提取器 = stripUiNoise → 弯引号成对感知转义 →
repairBareNewlinesInStrings → fence 截断救援（spanTrimmed）。
零网络成本，覆盖已观测的全部"重排版型"损坏（可逆双射）。

**第二层（兜底）**：修复工位。触发点两个——
1. 解析失败两轮（含同页契约重问一轮）后；
2. 机器验收失败（花括号不平衡 / JSON 不合法 / 缺键）。
动作：buildRepairPrompt 把**原始完整回答**（最大证据量，非截断的解析值）作为
修复任务书发给 executor 链（deepseek 优先，配置驱动），产物再过同一套
parseDeliverable + runAcceptance，过则带 `repair` 溯源字段返回，
不过则 fail-loud（含 repair_error）。只修一次，绝不重发原始 prompt。

**实测（scripts/smoke-repair.mjs，真实链路）**：
idx-12 最坏样本（混合定界符，机械层信息论不可解）——
默认提取器正确识别（missing }）→ 真发 deepseek 16.7s → 2098 字符完整产物
→ 验收过 → node --check 过 → 内容忠实性抽查零丢失（特征串次数逐一一致，
损坏行重建为正确定界+转义）。正常路径回归：8.9s 直过、不触发修复。

vm.Script 语法反馈循环的设计保留为第一层的可选深化（层 1.5），
当前两层架构已覆盖全部观测损坏，不预先建设。
