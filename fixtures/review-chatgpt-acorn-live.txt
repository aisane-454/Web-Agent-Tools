[严重度: 高] sourceType: "module" 固定为 ESM — 这会把所有待检代码都按 ES Module 解析，而不是验证其实际目标语境。典型误报包括合法 script 中的 with、部分 legacy sloppy-mode 语法；同时 import/export 会天然通过，即使实际交付物要求普通 script。作为通用语法验收门，语境假设过强。— 修改建议： 根据 deliverable 明确区分 "script" / "module"；如果无法确定，不应擅自固定为 module，可返回 unsupported，或分别解析并明确“至少一种 JS 语境有效”与“目标语境有效”是两种不同语义。 [严重度: 高] allowAwaitOutsideFunction: true 无条件开启 — 该选项扩大了 Acorn 的接受范围，使原本依赖特定执行环境才能成立的顶层 await 被一律视为合法；尤其如果未来切换到 sourceType: "script"，它甚至可能让普通脚本中的顶层 await 通过语法门。作为验收门存在漏报风险。— 修改建议： 若目标明确是支持 top-level await 的 ESM，就依靠相应 ECMAScript/module 规则解析，不要全局开启该宽松选项；只有业务明确需要“上下文外 await 豁免”时才开启，并把这种情况作为显式策略。 [严重度: 高] ecmaVersion: "latest" 与实际运行时能力脱钩 — “Acorn 能解析”不等于“目标 Node/浏览器能运行”。未来 ECMAScript 新语法一旦被当前 Acorn 接受，就可能通过验收，但部署运行时并不支持，形成典型漏报。— 修改建议： 验收门应绑定项目的实际 JS target/runtime，例如明确的 ECMAScript 年份，或由项目配置推导；若该函数只负责“最新 JS grammar 是否成立”，则应在接口/命名中明确这一边界，不能把它等价为可执行性验收。 [严重度: 中] TS/TSX/JSX 跳过完全依赖 deliverable.language — 如果调用方缺失、写错或没有提供 language，例如 TS 代码对应 undefined、"javascript"，代码就会送入 Acorn，并被报告为 invalid，把“解析器不支持该语言”错误地判成“代码存在语法错误”。— 修改建议： 将 deliverable.language 视为必须可靠的上游契约并在缺失时返回 unsupported/unknown-language；或者引入更明确的 artifact 类型。不要试图靠代码正文正则猜 TS，这同样容易误判。 [严重度: 中] JSX 被整体标记为 unsupported，但边界语义容易混淆 — "jsx" 被跳过是正确的，因为裸 Acorn 不解析 JSX；但 .js / "javascript" 交付物中实际包含 JSX 时仍会得到 invalid。同一 JSX 语法会因 metadata 不同得到两种完全不同的结果。— 修改建议： 如果系统允许 JSX 出现在 JavaScript deliverable 中，应使用 JSX-capable parser；否则明确规定 language metadata 必须准确反映 JSX，并把这一要求放进调用契约。 [严重度: 中] “语法有效”实际上只代表 Acorn parser acceptance — 此门无法捕获 parse 后才会暴露的运行环境约束、模块解析问题、绑定/类型错误等。例如某些环境特定语法或能力并不由 Acorn grammar 决定。因此如果上层把 status: "valid" 理解为“可以执行/可以验收”，边界过宽。— 修改建议： 将返回语义明确限定为 syntax-valid，甚至函数命名保持 runSyntaxCheck 的同时文档明确“不验证 runtime compatibility/module resolution/types”；不要让该结果单独承担完整代码验收。 [严重度: 低] e instanceof SyntaxError 对 parser 错误类型形成不必要依赖 — 当前 Acorn 正常 parse error 通常是 SyntaxError，所以现阶段没有明显问题；但此处依赖 Acorn 始终使用当前 realm 的原生 SyntaxError。一旦 parser 包装方式、realm 或依赖行为改变，普通解析失败可能被重抛为系统异常。— 修改建议： 如果“只有真正的 parser syntax error 才转为 invalid，其他异常必须 fail-loud”是刻意设计，建议保留这一原则，但使用 Acorn 明确保证的错误契约并加测试，而不是无意依赖 instanceof。 [严重度: 低] 非 SyntaxError 直接重抛的 fail-loud 行为是正确的，但需要上层保证不会再次吞掉 — 本函数本身没有把 parser 内部异常、编程错误等伪装成 invalid，这一点边界是安全的；真正风险在调用方若把 throw 统一转换成普通验收失败，就会失去这种区分。— 修改建议： 为三种路径建立验收测试：valid、预期 parser syntax error → invalid、任意非语法异常 → 必须向上传播；上层也应保持 fail-loud。
